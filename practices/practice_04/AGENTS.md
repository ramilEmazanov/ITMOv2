# Стек и правила проекта

Проект — веб-приложение с двумя фичами: **A — поиск авиабилетов**, **B — сохранение найденных цен и сравнение с прошлым поиском**. Сценарий, ограничения Ignav REST API и текущее состояние описаны в [PROJECT_README.md](PROJECT_README.md).

## Фронтенд

- **React + TypeScript + Vite** — форма поиска, фильтры и карточки билетов; для оформления используется обычный CSS.
- Фронтенд обращается только к FastAPI. Не помещай `IGNAV_API_KEY` в браузерную сборку и не вызывай Ignav REST напрямую из браузера.
- Показывай валюту из `price.currency`, не считай найденную цену окончательной. Ссылки на бронирование не входят в фичи A и B.
- Для фичи B показывай разницу с предыдущей сопоставимой ценой; если её нет, явно сообщай об этом.

## Бэкенд и Ignav REST API

- **Python + FastAPI, Pydantic, httpx** — валидация запросов, серверные обращения к Ignav и единый формат ответа для фронтенда.
- Целевые запросы для A: `POST /api/fares/one-way` с `origin`, `destination`, `departure_date`; `POST /api/fares/round-trip` с дополнительным `return_date`. `GET /api/airports?q=...` можно добавить для подсказок городов после базового поиска. Используй базовый URL `https://ignav.com`, заголовок `X-Api-Key: <ключ>` и серверную переменную `IGNAV_API_KEY`. Не сохраняй ключ в коде, коммитах или логах. См. [справочник Ignav](https://ignav.com/docs/api-reference).
- Валидация: трёхбуквенные поддерживаемые IATA-коды аэропортов или агломераций, полные даты `YYYY-MM-DD`, дата возвращения не раньше вылета. Для прямого рейса передавай `max_stops: 0`; бюджет можно передать в `max_price` в валюте выбранного `market`. Не отправляй прежние параметры Travelpayouts `departure_at=YYYY-MM`, `direct`, `currency` или `sorting` в Ignav.
- Нормализуй `itineraries` в модель интерфейса, сохраняя `ignav_id`, цену, валюту, плечи и сегменты. Пересадки считай по сегментам каждого плеча. Получение `booking-links` оставь для отдельного расширения после A и B.
- Пустой список маршрутов — нормальный результат. Обрабатывай структурированные `error.code`: ошибки ввода показывай пользователю, сетевые ошибки и `424/unable_to_complete_request` повторяй с ограниченным backoff, `424/unsupported_search` не повторяй с теми же датами, `402/billing_required` и `429/monthly_spend_limit_reached` не зацикливай. [Ошибки Ignav](https://ignav.com/docs/errors), [рекомендации для production](https://ignav.com/docs/production-checklist).
- Ignav ищет конкретные даты. Пока не реализован ограниченный поиск по диапазону, требуй день вылета вместо месяца. Позже перебирай явно ограниченный набор дней и показывай охват; не утверждай, что найден минимум всего месяца при частичной проверке. Платные запросы выполняй только после явной команды поиска; кешируй повторные запросы на несколько минут.

## Фича B: сохранение и сравнение

- После завершения A реализуй B в отдельном Git worktree. Добавь локальную SQLite-базу на бэкенде. После успешного ответа с билетами сохраняй время, параметры поиска, валюту и минимальную цену. Пустой результат можно сохранять без цены, но не использовать для числового сравнения.
- Сравнивай только одинаковые маршрут, даты, тип поездки, рынок/валюту и фильтры. Возвращай предыдущую и текущую цену, абсолютную и процентную разницу; если прежней цены нет, возвращай отдельное состояние. Для неверной даты, пустых данных и разных валют выдавай понятную ошибку.
- Добавь проверки расчёта и сохранения истории на повторном поиске; после объединения worktree проверь A и B вместе. Не вводи аккаунты или внешнюю базу для этой версии.

## MCP и требования практики

- В `opencode.json` подключён `context7` для документации библиотек. При работе с незнакомой библиотекой вызывай его tool и сохраняй подтверждение вызова для защиты. Поиск билетов в A идёт через Ignav REST API, а не через MCP.
- Отдельное требование [README.md](README.md) — собственный MCP tool с успешным и ошибочным вызовами. После B можно использовать сравнение цен как основу для `compare_prices`; сами A и B не заменяют демонстрацию tool. Нужны также запуск skill, проверка после правки с результатом для агента и `reflection.md`.

## Среда для агента

- Рабочая папка — `practices/practice_04`. Фича A переведена на Ignav: React делает POST в FastAPI, а сервер использует `IGNAV_API_KEY`. История цен (фича B) ещё не реализована.
- Локальные скиллы находятся в `.agents/skills/`. Перед работой с FastAPI используй `fastapi-python`, со сложными схемами и валидацией — `pydantic`, с React-компонентами и производительностью — `vercel-react-best-practices`. Это инструкции для агента, а не зависимости приложения.
- Из `frontend/` запускай `npm install`, затем `npm run dev`; для проверки — `npm run build`. Из `backend/` устанавливай `requirements.txt`, запускай `uvicorn app.main:app --reload`; для тестов установи `requirements-dev.txt` и запускай `pytest`.
- Git-хук `.githooks/pre-commit` проверяет сборку фронтенда. В новом клоне включи его из корня репозитория через `git config core.hooksPath .githooks`.
