# Проект: поиск недорогих авиабилетов

Веб-приложение помогает найти авиабилеты и увидеть, как изменилась минимальная найденная цена с прошлого поиска. Работа делится на две фичи: **A — поиск билетов**, **B — сохранение результатов и сравнение цен**. Пользователь задаёт маршрут и даты, при желании ограничивает цену и пересадки.

## Источник данных: Ignav

Целевой источник — [Ignav Flight API](https://ignav.com/docs/api-reference). Бэкенд отправляет JSON-запросы на `POST https://ignav.com/api/fares/one-way` или `POST https://ignav.com/api/fares/round-trip`. Обязательны IATA-коды `origin`, `destination` и дата `departure_date` в формате `YYYY-MM-DD`; для обратного рейса нужна `return_date`. Дополнительные параметры: `max_stops` (`0` для прямых рейсов), `max_price`, пассажиры, `market` — двухбуквенный код рынка, который определяет валюту цены. Произвольного параметра `currency` у Ignav нет. Ключ аккаунта передаётся сервером в заголовке `X-Api-Key` и хранится в переменной окружения `IGNAV_API_KEY`, а не во фронтенде. Для ввода городов можно использовать `GET /api/airports?q=...` через бэкенд; известные IATA-коды аэропортов и поддерживаемые коды агломераций можно передавать сразу. [Поиск в одну сторону](https://ignav.com/docs/one-way), [поиск туда-обратно](https://ignav.com/docs/round-trip), [поиск аэропортов](https://ignav.com/docs/airports), [аутентификация](https://ignav.com/docs/authentication).

Ответ содержит массив `itineraries` с `price.amount`, `price.currency`, сегментами перелёта, временем и `ignav_id`. Число пересадок определяется по числу сегментов каждого плеча. `ignav_id` — временный идентификатор результата в рамках аккаунта, а не постоянный ID рейса. Ссылки на бронирование не входят в базовые фичи A и B. Если добавлять их позже, после выбора маршрута нужно вызвать `POST /api/fares/booking-links` с `ignav_id` и использовать возвращённый `booking_options[].links[].url`; варианты могут отсутствовать. Окончательную цену пользователь проверяет у продавца. [Документация ссылок](https://ignav.com/docs/booking-links).

Ignav ищет тарифы **на конкретную дату**, а не сразу на месяц. Для первой интеграции пользователь выбирает день. Поиск самых дешёвых дней в месяце — следующий этап: бэкенд выполняет ограниченную серию запросов по явно выбранному диапазону дат, кеширует одинаковые запросы на несколько минут и показывает, какие дни проверены. Если охвачена лишь часть месяца, интерфейс не выдаёт результат за минимум всего месяца. Успешные запросы тарифицируются, поэтому поиск запускается только по кнопке, без вызова на каждый ввод символа или обновление страницы. Пустой `itineraries` означает отсутствие подходящих вариантов, а не ошибку. Цены и наличие мест меняются; показываем их как ориентир. [Рекомендации Ignav](https://ignav.com/docs/production-checklist).

## Фича A: поиск билетов

- Форма принимает маршрут, конкретную дату вылета и, для билета туда-обратно, дату возвращения. Дополнительные фильтры: максимальная цена и прямые рейсы.
- По кнопке «Найти билеты» фронтенд обращается к FastAPI, тот запрашивает Ignav REST API. Результат показывает карточки с ценой и валютой, датами, перевозчиком и пересадками, отсортированные по цене.
- Если вариантов нет, интерфейс показывает понятное пустое состояние. Неверные даты, коды и ошибки сервиса показываются отдельно.

**Готово, когда:** реальные результаты Ignav проходят через бэкенд во фронтенд; проверены успешный поиск, пустой ответ и ошибочный ввод. Без ключа Ignav интерфейс показывает ошибку настройки, а не вымышленные результаты.

## Фича B: история и сравнение цен

- После каждого успешного поиска с найденными билетами бэкенд сохраняет в локальную SQLite-базу время поиска, параметры маршрута, валюту и минимальную найденную цену. Это цена из ответа Ignav на момент поиска, а не обещание продавца.
- Для сравнения бэкенд берёт предыдущую запись с **теми же параметрами поиска**: маршрут, даты, направление поездки, рынок/валюта и фильтры. Интерфейс показывает прошлую цену, текущую цену и разницу в деньгах и процентах: «дешевле», «дороже» или «без изменений». При первом поиске пишет, что сравнивать пока не с чем.
- Пустой ответ сохраняется как факт поиска без минимальной цены, но не участвует в числовом сравнении. Некорректная дата, пустые данные для сравнения и несовпадающие валюты дают понятную ошибку. История хранится локально; аккаунты и синхронизация не входят в эту версию.

**Готово, когда:** два последовательных поиска с одинаковыми параметрами дают корректное сравнение; первый поиск, пустой ответ и неверные данные обрабатываются предсказуемо. Фичу B удобно делать в отдельном Git worktree после проверки A, затем проверить объединённый результат.

## Текущее состояние репозитория

Фича A реализована: React отправляет явный POST в FastAPI, который обращается к Ignav, нормализует и сортирует ответы. Реальные билеты появляются только при настроенном `IGNAV_API_KEY`; без ключа показывается ошибка конфигурации. Поиск по диапазону дат, история цен (фича B), подсказки аэропортов и ссылки на бронирование пока не реализованы.

Для запуска нужны Node.js, npm и Python:

```bash
cd practices/practice_04/backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
# Запишите IGNAV_API_KEY=ваш_ключ в backend/.env (файл исключён из Git)
uvicorn app.main:app --reload
```

В другом терминале:

```bash
cd practices/practice_04/frontend
npm install
npm run dev
```

Vite перенаправляет `/api` на FastAPI по адресу `127.0.0.1:8000`. Для проверки используйте `pytest` в `backend/` и `npm run build` в `frontend/`. Сетевой поиск тарифицируется Ignav, а повторный одинаковый запрос кешируется сервером на три минуты.

## Среда агента и домашняя работа

В `opencode.json` настроен MCP `context7` для поиска документации библиотек. Для получения билетов приложение использует **Ignav REST API** через FastAPI. Требование практики о собственном MCP tool остаётся отдельным заданием: позднее можно сделать `compare_prices` на основе данных фичи B и показать успешный и ошибочный вызовы. Подключённый MCP, skill, автоматическая проверка после правки и `reflection.md` нужны для сдачи по [README.md](README.md); наличие конфигурации без реальных вызовов не считается демонстрацией.

## Проверка перед коммитом

В репозитории есть Git-хук `.githooks/pre-commit`: если в коммит добавлены файлы `practice_04/frontend`, он запускает `npm run build` и останавливает коммит при ошибке TypeScript или сборки. После `npm install` включите хук один раз из корня репозитория:

```bash
git config core.hooksPath .githooks
```
