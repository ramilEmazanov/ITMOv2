# План реализации практики 7.2 целиком

## Что делаем и как связаны задания

Цель — выполнить **часть 1, часть 2, задание со звёздочкой и сверхрезультат** в одном проекте на n8n.

Они совместимы и используют общий тестовый GitHub-репозиторий. Основная работа классифицирует обращения и строит отчёты. Сверхрезультат продолжает ветку `bug`: создаёт исправление, отправляет его на ревью и при успешных проверках автоматически сливает в `master`.

Это несколько связанных workflow, а не взаимоисключающие варианты решения. Создавать разные Git-ветки для основной работы и сверхрезультата не требуется. Отдельная ветка нужна **для каждого автоматически исправляемого бага**, как требует задание.

Источник требований — [README.md](README.md).

| Блок | Что реализуем | Баллы по заданию |
|---|---|---:|
| Часть 1 | Классификация, эскалация, Sub-workflow | 5 |
| Часть 2 | Данные за неделю, группировка, Gmail | 6 |
| Со звёздочкой | Data Table, Δ, AI-аннотация | 5 |
| Сверхрезультат | Исправление → отдельная ветка → ревью → merge | 10 |

Основная шкала — **16 баллов**, сверхрезультат указан отдельным блоком на **10 баллов**. Суммарный объём критериев — 26 баллов; правило перевода в итоговую оценку в README не описано. Поэтому это план выполнения всех требований, а не обещание итоговой оценки 26 или 10.

**Важно:** критерии основной работы засчитываются по порядку. Если предыдущий критерий не выполнен или не подтверждён запуском, следующие не засчитываются. Разрабатывать и сохранять доказательства будем в том же порядке.

## Общая архитектура

```text
GitHub Issue opened
    ↓
Workflow 1: проверка события → классификатор → проверка confidence → Switch
    ├── task    → label task
    ├── feature → label feature
    ├── unknown → label needs-triage → завершение без комментария
    └── bug     → label bug → workflow автоматического исправления
                                  ↓
                         AI-исполнитель в runner
                                  ↓
                         тесты → push в fix/issue-N → PR
                                  ↓
                         отдельное AI-ревью
                                  ↓
                         n8n проверяет тесты, вердикт и SHA
                                  ↓
                         merge в master либо остановка

Cron: каждый понедельник в 09:00
    ↓
Workflow статистики: GitHub API → Code → чтение прошлой недели
    ↓
Δ → сохранение недели в Data Table → AI-аннотация → HTML → Gmail
```

n8n управляет переходами между этапами и решением о merge. Runner выполняет работу с кодом, но не принимает финальное решение о слиянии.

Предлагаемые workflow:

1. `01_issue_intake` — webhook, классификация, лейблы и запуск исправления для `bug`.
2. `02_classify_issue` — Sub-workflow: `title`, `body` → `type`, `confidence`.
3. `03_weekly_report` — сбор данных, агрегация, история, Δ, аннотация и Gmail.
4. `04_fix_bug` — запуск runner, получение результата, PR и запуск ревью.
5. `05_review_and_merge` — отдельное ревью, проверка условий и merge.

Последние два можно объединить при сохранении понятных этапов в Executions. Первые три соответствуют сценариям, экспорт которых прямо требуется для основной работы.

Использовать две разные Data Table:

- `weekly_stats` — недельные снимки для отчёта и сравнения.
- `issue_runs` — дедупликация и состояние обработки Issues, ветка, PR, SHA, ошибки.

## Этап 13. Сверхрезультат: включить автоматический merge

В `05_review_and_merge` разрешать merge только при одновременном выполнении условий:

- [ ] PR открыт и направлен в `master` нужного репозитория.
- [ ] Все обязательные тесты и проверки завершены успешно.
- [ ] Ревью дало `approve`, серьёзных замечаний нет.
- [ ] Текущий SHA совпадает с SHA ревью и проверок.
- [ ] Нет конфликтов и правила репозитория разрешают merge.

- [ ] Выполнять merge из n8n с ожидаемым SHA, чтобы не слить новый непроверенный коммит.
- [ ] После изменения PR заново запускать проверки и ревью.
- [ ] После merge записывать итоговый статус и проверять наличие исправления в `master`.
- [ ] Связать PR с Issue для автоматического закрытия после merge.
- [ ] Ограничить повторы временных ошибок; повторный callback не должен повторять завершённые действия.

**Подтверждение:** путь от открытия Issue до исправления в `master` проходит без ручного push, одобрения и нажатия Merge. Серьёзные замечания и упавшие тесты останавливают процесс.

Автоматическое повторное исправление после замечаний — дополнительное улучшение. Для требований достаточно успешного полного пути и остановки при серьёзных замечаниях.

## Этап 14. Общая проверка совместимости

| Проверка | Ожидаемое поведение |
|---|---|
| Новый `bug` | Label → исправление → PR → ревью → merge |
| Новый `task` или `feature` | Правильный label; исправление не запускается |
| Неоднозначный Issue с confidence < 0.8 | `needs-triage`, нет комментария и исправления |
| Повторный webhook или callback | Нет второго PR и повторных завершённых действий |
| Тесты упали или ревью требует изменений | Merge заблокирован, причина сохранена |
| После ревью изменился SHA | Старое разрешение больше не позволяет merge |
| Баг автоматически закрыт после merge | Он остаётся в статистике своей недели создания |
| Создан PR исправления | PR не считается отдельным Issue в отчёте |
| Повторный расчёт недели | Нет дубликата снимка, Δ считается к прошлой неделе |
| Пустая неделя или нет предыдущей | Корректные нули и честное отсутствие сравнения |
| Финальный ручной запуск отчёта | Реальное письмо с таблицами, Δ и AI-аннотацией |

Сначала сохранить отдельные доказательства основной работы, затем выполнить общую демонстрацию с включённым исправлением. Для финального показа использовать новый баг, который ещё не исправлен в `master`.

## Этап 15. Подготовить сдачу

```text
submission/
  README.md                 # запуск, архитектура, ссылки на Issues и PR
  workflows/                # JSON всех n8n workflow без секретов
  runner/                   # код или конфигурация AI-исполнителя
  prompts/                  # инструкции и схемы ответов AI
  evidence/
    part_1/                 # классификация, unknown, вызов Sub-workflow
    part_2/                 # cron, четыре запроса, Code, полученное письмо
    star/                   # две недели Data Table, Δ, AI-аннотация
```
